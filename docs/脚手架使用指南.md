> ⚠️ **为什么不再拆模块？**

> 包名已按能力划分，**将来真有独立交付 / 可选依赖的需求时再拆**，拆比合容易。

## 二、目录与命名规范

### 包职责边界

| 包 | 放什么 | 不放什么 |
|---|---|---|
| `lib.core.*` | 纯通用能力，可跨项目复用 | 任何业务概念（订单、库存…） |
| `app.feature.*` | 业务实现 | 通用能力（要下沉到 `lib.core`） |

判断标准：**把 `lib/core` 单独拷到另一个项目还能用吗？** 不能就说明混入了业务。

### 包命名

```
com.example.testdemo
├── lib.<能力>        通用能力，独立包名，避免与业务混淆
├── feature.<功能>    业务功能按领域分包
└── ui.theme          全局 UI 主题
```

### 页面三件套

```
feature/<name>/
├── <Name>Screen.kt        Compose UI（只读 state，只发 intent）
├── <Name>ViewModel.kt     Intent / State / Event 定义 + 处理逻辑
└── <Name>Repository.kt    数据来源（网络 / 存储 / 数据库）
```

## 三、lib.base —— MVI 基座

架构对齐 `MVI-Coroutines-Flow`：**契约 + 抽象 ViewModel + Activity/Fragment 基类 + Compose 接线**。

### 三个契约 + 两个接口

| 类型 | 作用 |
|---|---|
| `MviIntent` | 用户意图标记 |
| `MviViewState` | 页面状态标记（另有 `MviViewStateSaver` 支持 Bundle 存取，用于进程被杀恢复）|
| `MviSingleEvent` | 一次性事件标记 |
| `MviView<I,S,E>` | 视图侧契约：`render(state)` / `handleSingleEvent(event)` / `viewIntents()` |
| `MviViewModel<I,S,E>` | VM 侧契约：`viewState` / `singleEvent` / `processIntent(intent)` |

### 单向数据流

```
View --(Intent)--> intents --> 业务 Flow --> scan(reduce) --> viewState --> View
                                        └--> sendEvent --> singleEvent --> View
```

- **意图**：`Channel` 汇聚（**不要用 `MutableSharedFlow`**，原因见下方 ⚠️）
- **一次性事件**：`Channel` 投递，保证「有且仅有一次」，不像状态那样重放
- **状态**：`StateFlow` + `scan(PartialChange.reduce)` 增量合并

> ⚠️ **为什么意图必须用 `Channel`**
>
> `MutableSharedFlow(replay = 0)` 在**没有订阅者**时 `tryEmit` 返回 `true`
> 但会**静默丢弃**值（它的缓冲只服务于「已存在但跟不上」的订阅者）。
>
> 而 `viewState` 是 `stateIn(viewModelScope, SharingStarted.Eagerly, ...)`，
> 它的收集协程是否已经订阅并不确定。Compose 侧
> `LaunchedEffect(Unit) { viewModel.dispatch(Load) }` 完全可能先执行。
>
> **实测后果**：全新安装打开首页，`Load` 意图凭空消失，不发请求，
> 首屏永远空白，而且**没有任何日志或报错**。
>
> `Channel(UNLIMITED)` 会把意图缓冲到订阅者到来，不存在这个竞态。
> 回归测试：`lib/core/src/test/.../IntentBufferingTest.kt`（3 个用例，
> 在旧实现下会全部失败）。

### 写一个页面：Contract / ViewModel / View 三件套

**① XxxContract.kt** —— 契约 + 局部状态变更

```kotlin
sealed interface XxxIntent : MviIntent {
    data object Load : XxxIntent
    data object Retry : XxxIntent
}

data class XxxState(
    val items: List<Item> = emptyList(),
    val isLoading: Boolean = false,
    val error: String? = null,
) : MviViewState

sealed interface XxxEvent : MviSingleEvent {
    data class ShowMessage(val message: String) : XxxEvent
}

/** 局部状态变更：只描述「变了什么」，由 reduce 合并进完整状态 */
internal sealed interface XxxPartialChange {
    data object Loading : XxxPartialChange
    data class Success(val items: List<Item>) : XxxPartialChange
    data class Failure(val message: String) : XxxPartialChange

    fun reduce(state: XxxState): XxxState = when (this) {
        Loading -> state.copy(isLoading = true, error = null)
        is Success -> state.copy(isLoading = false, items = items)
        is Failure -> state.copy(isLoading = false, error = message)
    }
}
```

**② XxxViewModel.kt**

```kotlin
class XxxViewModel(private val repository: XxxRepository) :
    AbstractMviViewModel<XxxIntent, XxxState, XxxEvent>() {

    override val viewState: StateFlow<XxxState> = intents
        .flatMapLatest { intent ->
            when (intent) {
                XxxIntent.Load, XxxIntent.Retry -> loadFlow()
            }
        }
        .onEach { if (it is XxxPartialChange.Failure) sendEvent(XxxEvent.ShowMessage(it.message)) }
        .scan(XxxState()) { state, change -> change.reduce(state) }
        .stateIn(viewModelScope, SharingStarted.Eagerly, XxxState())

    private fun loadFlow(): Flow<XxxPartialChange> = flow {
        emit(XxxPartialChange.Loading)
        when (val r = repository.load()) {
            is ApiResult.Success -> emit(XxxPartialChange.Success(r.data))
            is ApiResult.Failure -> emit(XxxPartialChange.Failure(r.error.message))
            ApiResult.Cancelled -> Unit
        }
    }
}
```

**③ 视图侧，二选一**

**方式 A：Activity / Fragment 基类**（推荐）

```kotlin
class XxxActivity : AbstractMviActivity<XxxIntent, XxxState, XxxEvent, XxxViewModel>() {

    override val vm: XxxViewModel by viewModels { XxxViewModel.factory(...) }

    @Composable
    override fun render(state: XxxState) {
        Button(onClick = { sendIntent(XxxIntent.Retry) }) { Text("重试") }
    }

    override fun handleSingleEvent(event: XxxEvent) { /* Snackbar / 导航 */ }
}
```

基类自动绑定三件事，子类不用写订阅代码：

| 绑定 | 说明 |
|---|---|
| `viewState → render` | 状态变化自动重组 |
| `singleEvent → handleSingleEvent` | 只在 STARTED 及以上消费 |
| `viewIntents → processIntent` | 视图意图自动上行 |

`AbstractMviFragment` 行为一致，订阅挂在 `viewLifecycleOwner` 上。

**方式 B：`MviScreen`**（单 Activity + 路由项目）

```kotlin
@Composable
fun XxxScreen(viewModel: XxxViewModel) {
    LaunchedEffect(Unit) { viewModel.dispatch(XxxIntent.Load) }

    MviScreen(viewModel, onEvent = { /* 一次性事件 */ }) { state ->
        // 渲染
    }
}
```

### 意图发送的三个入口

| 入口 | 场景 |
|---|---|
| `suspend fun processIntent(intent)` | 契约方法，协程中调用（基类内部用）|
| `fun dispatch(intent)` | **非挂起**，Compose 的 `onClick` 直接调用 |
| `sendIntent(intent)` | `AbstractMviActivity` / `AbstractMviFragment` 内的受保护方法 |

### UiState 四态（可选便利工具）

简单页面可直接用 `UiState` + `UiStateHost`，不必手写状态字段：

| 状态 | 渲染 |
|---|---|
| `Idle` / `Loading` | 居中转圈 |
| `Empty(message)` | 空态文案 |
| `Error(message)` | 错误 + 重试按钮 |
| `Success(data)` | 交给业务 content |

### 通用工具

- **`EnterKeyDebouncer`** —— PDA 扫描枪回车防抖（时间源可注入，可单测）
- **`Flow.collectIn(owner)`** —— 生命周期感知收集（移植自参考架构 `core-ui`）

```kotlin
private val debouncer = EnterKeyDebouncer(500)
input.setOnKeyListener { _, key, event ->
    if (key == KeyEvent.KEYCODE_ENTER && event.action == KeyEvent.ACTION_UP) {
        if (!debouncer.shouldDebounce()) submit()
        true
    } else false
}
```

## 四、网络层：Ktor（跨端）

网络用 **Ktor**，所以 Android / iOS 共用同一份客户端代码 —— 差异只在一个函数：

```kotlin
// lib/shared/commonMain/net/HttpEngine.kt
expect fun platformHttpEngine(): HttpClientEngineFactory<*>

// androidMain → OkHttp      iosMain → Darwin（URLSession）
```

### 用法

```kotlin
val client = NetworkClient(
    NetworkConfig(
        baseUrl = environment.baseUrl,
        // 下面三个一起控制「请求日志」——见第七章
        enableHttpLogs = BuildConfig.DEBUG && environment.enableHttpLogs,
        httpLogLevel = HttpLogLevel.ALL,
        httpLogger = LogcatHttpLogger,          // Android → Logcat
        headerProvider = { mapOf("X-App-Version" to BuildConfig.VERSION_NAME) },
        tokenProvider = { storage.getToken() },
    )
)

// 统一 GET：网络异常与 HTTP 错误码都收敛成 ApiResult
val result: ApiResult<List<PostDto>> = client.getResult("posts")
```

数据模型加 `@Serializable` 即可（Ktor 用 kotlinx-serialization）。

### 错误映射（跨端）

`ErrorMapper` 用 **Ktor + kotlinx.serialization 的异常**，所以两端共用：

| 异常 / 状态 | ApiErrorType |
|---|---|
| `HttpRequestTimeoutException` / `ConnectTimeoutException` / `SocketTimeoutException` | `TIMEOUT` |
| `JsonConvertException` / `SerializationException` | `PARSE` |
| `kotlinx.io.IOException` | `CONNECT` |
| 非 2xx 响应 | `HTTP`（带状态码）|
| 业务 `result=false` | `BUSINESS`（带后端 message / code）|
| 其他 | `UNKNOWN` |

### 为什么不用 Retrofit

Retrofit 是 JVM 专属；Ktor 是 KMP 的，**同一份客户端代码 iOS 直接复用**，
且底层 Android 仍是 OkHttp（引擎可换）。

> 📝 旧版基于 `java.net.*` 的 `ErrorMapper` 只能在 JVM 用，已随迁移废弃。

## 五、lib.image —— 图片能力抽象（外观模式）

业务**永远不直接依赖 Coil / Glide**，只依赖门面，因此换图片框架不影响业务代码。

### 用法

```kotlin
// 最简
AppImage(model = url, modifier = Modifier.size(48.dp).clip(CircleShape))

// 带占位图 / 错误图 / 缓存策略
AppImage(
    model = url,
    modifier = Modifier.fillMaxWidth().height(180.dp),
    options = ImageOptions.builder()
        .placeholder(R.drawable.ic_placeholder)
        .error(R.drawable.ic_error)
        .noCache()                 // 或 .diskCache(false) / .skipMemoryCache(true)
        .build(),
    contentScale = ContentScale.Crop,
)

// 预加载（列表预取 / 详情页提前加载）
ImageLoader.preload(context, url)

// 清缓存
ImageLoader.clearMemory(context)
ImageLoader.clearDisk(context)
```

### 换底层框架

```kotlin
// Application.onCreate
ImageLoader.init(MyGlideEngine())   // 实现 ImageEngine 接口即可
```

| 组成部分 | 职责 |
|---|---|
| `ImageOptions` | 与框架无关的加载选项（占位图、错误图、内存/磁盘缓存策略） |
| `ImageEngine` | 抽象：渲染 / 预加载 / 清缓存 |
| `DefaultImageEngine` | 内置 Coil 实现 |
| `ImageLoader` / `AppImage` | 门面：业务唯一入口 |

> **为什么默认用 Coil 而不是 Glide？** 模板是 Compose 体系，Coil 的 Compose 接入成本最低。
> k3_wms_android 用的是 Glide（ImageView 体系），如需对齐，实现一个 `ImageEngine` 后
> `ImageLoader.init(...)` 即可，业务页面零改动 —— 这正是外观模式的价值。

## 六、存储：DataStore + Room

两块各司其职，**别用错**：

| 场景 | 方案 | 为什么 |
|---|---|---|
| 配置 / 登录态 / 小 KV | **DataStore** | 全 suspend + Flow，不阻塞主线程 |
| 结构化数据 / 离线缓存 / 查询 | **Room** | 有事务、能索引、支持响应式查询 |

> ⚠️ **不要再用 SharedPreferences**：`commit()` 阻塞主线程有 ANR 风险，
> 变更通知靠 `OnSharedPreferenceChangeListener`（易泄漏）。

### DataStore（KV）

```kotlin
// Application
storage = createAppStorage(this)

// 读写
storage.putString("token", value)
val token = storage.getString("token")
storage.observeString("token").collect { ... }   // 订阅变化

storage.putBoolean("dark_mode", true)            // 也支持 Boolean / Int / Long
```

业务只依赖 `AppStorage` 接口 —— 换 MMKV 或自研实现不影响业务代码。

### Room（结构化数据）

通用能力在 `lib.db`：

```kotlin
@Database(entities = [PostEntity::class], version = 1, exportSchema = false)
@TypeConverters(AppRoomConverters::class)          // ← 通用转换器
abstract class AppDatabase : RoomDatabase() {

    abstract fun postDao(): PostDao

    companion object {
        fun create(context: Context) =
            buildDatabase<AppDatabase>(context, "app.db") {   // ← 统一构建入口
                fallbackToDestructiveMigration(dropAllTables = true)
            }
    }
}
```

`AppRoomConverters` 已覆盖业务常用类型：**BigDecimal**（金额/数量，避免 Double 丢精度）、**List\<String\>**。

**新增一张表**：

```kotlin
@Entity(tableName = "orders")
data class OrderEntity(@PrimaryKey val id: String, val qty: BigDecimal)

@Dao
interface OrderDao {
    @Query("SELECT * FROM orders") suspend fun getAll(): List<OrderEntity>
    @Query("SELECT * FROM orders") fun observeAll(): Flow<List<OrderEntity>>   // 响应式
    @Insert(onConflict = OnConflictStrategy.REPLACE) suspend fun upsertAll(rows: List<OrderEntity>)
}
```

再把实体加进 `@Database(entities = [...])` 并升 `version`。

### 示例：数据库为单一数据源（SSOT）

`data/PostRepository.kt` 演示标准写法 —— **Room 是唯一数据源，网络只负责刷新**：

```kotlin
class PostRepository(networkProvider, postDao) {

    /** UI 订阅它拿数据，数据库一变自动推送。 */
    fun observePosts(): Flow<List<PostDto>> =
        postDao().observeAll().map { rows -> rows.map { it.toDto() } }

    /** 只负责「拉网络 → 写库」，不直接返回列表。 */
    suspend fun refresh(): ApiResult<Unit> =
        when (val r = fetchFromNetwork()) {
            is ApiResult.Success -> {
                postDao().upsertAll(r.data.map { it.toEntity() })
                ApiResult.Success(Unit)
            }
            is ApiResult.Failure -> r
            ApiResult.Cancelled -> ApiResult.Cancelled
        }
}
```

ViewModel 用 `combine` 把「刷新态」和「数据流」合起来：

```kotlin
override val viewState: StateFlow<HomeState> =
    combine(
        // ① 刷新流程：只维护 isLoading / error / loaded
        intents.flatMapLatest { refreshFlow() }
            .scan(HomeState()) { state, change -> change.reduce(state) },
        // ② 数据来源：数据库（唯一）
        repository.observePosts(),
    ) { state, posts -> state.copy(posts = posts) }
        .stateIn(viewModelScope, SharingStarted.Eagerly, HomeState())
```

**状态序列固定 3 帧**：

```
① 数据库首帧（posts 已就绪 —— 有缓存时不会闪空列表）
② 刷新中（isLoading = true）
③ 刷新结束（loaded = true；失败则带 error）
```

渲染时**有本地数据就先显示**，刷新在后台进行：

```kotlin
val uiState = when {
    state.posts.isNotEmpty() -> UiState.Success(state.posts)   // 缓存优先
    state.isLoading -> UiState.Loading
    state.error != null -> UiState.Error(state.error)
    state.loaded -> UiState.Empty()
    else -> UiState.Idle
}

// 刷新失败但库里有数据 → 顶部提示离线
if (state.isOfflineWithCache) { OfflineBanner() }
```

> 💡 **收益**：离线可用、页面切换不闪烁、多页面共享同一份数据、
> 刷新失败不会把已有内容清空。

> ⚠️ **测试注意**：`StateFlow` 会按值去重 —— 若数据库首帧与初始值相等
> （例如库为空），收集器的首个状态就是「初始态」而非「数据库帧」。

> ⚙️ **构建注意**：AGP 9 的「内置 Kotlin」默认禁止 `kotlin.sourceSets` DSL，
> 而 KSP 通过它注册 `build/generated/ksp`。已在 `gradle.properties` 用官方开关放开：
> `android.disallowKotlinSourceSets=false`

## 七、lib.log —— 日志与崩溃兜底

```kotlin
AppLogger.d("Tag", "message")
AppLogger.enabled = BuildConfig.DEBUG                 // release 包一律关闭
CrashGuard.install { throwable -> BuglyReporter.report(throwable) }   // 崩溃兜底
```

`CrashGuard` 只记日志并转交上报，**不吞异常** —— 处理完仍交给系统默认 handler，不改变原本的崩溃行为。

### 网络请求日志（Logcat）

三条开关缺一不可：

| 开关 | 作用 |
|---|---|
| `BuildConfig.DEBUG` | **硬兜底**，release 包永远不打印 |
| `environment.enableHttpLogs` | 环境级开关（dev/test 开，prod 关）|
| `httpLogLevel` | 详细程度：`NONE` / `BASIC` / `HEADERS` / `BODY` / `ALL` |

```kotlin
NetworkConfig(
    enableHttpLogs = BuildConfig.DEBUG && environment.enableHttpLogs,
    httpLogLevel = HttpLogLevel.ALL,      // 排查序列化问题用 ALL
    httpLogger = LogcatHttpLogger,        // 不传就什么也不打
)
```

过滤日志：

```bash
adb logcat -s Http
```

输出形如：

```
REQUEST: https://jsonplaceholder.typicode.com/posts
METHOD: HttpMethod(value=GET)
RESPONSE: 200 OK
{"id":1,"title":"...","body":"..."}
```

### 日志自动脱敏

`redactSensitive()` 在**写日志之前**替换敏感值，所以开着日志也不会泄露凭证：

| 场景 | 处理 |
|---|---|
| `Authorization: Bearer xxx` | 值变 `***` |
| `Cookie` / `Set-Cookie` / `X-Api-Key` | 值变 `***` |
| `?token=xxx&page=2` | token 变 `***`，`page` 保留 |
| URL 内嵌 `user:pass@host` | 凭证变掩码，域名保留 |
| 响应体 `{"access_token":"xxx"}` | 值变 `***` |

覆盖这些行为的测试见 `lib/shared/src/commonTest/.../HttpLogSanitizerTest.kt`（12 个用例）。

> ⚠️ **新增请求头时注意**：脱敏按**名字**匹配（含 `authorization` / `cookie` / `token` /
> `secret` / `password` / `api-key` 的都会被脱敏）。如果你的凭证头叫别的名字
> （例如 `X-Session`），要往 `HttpLogSanitizer.kt` 的正则里补一条。

    create("prod") {
        dimension = "environment"
        buildConfigField("String", "APP_ENV", "\"prod\"")
    }
}
```

> 为什么 flavor 名是 `staging` 而不是 `test`：AGP 保留 `test*` 开头的 flavor 名。
> `APP_ENV` 字段把 flavor 名和环境 key 解耦了，两者不必同名。

### 使用

// Application
val environment = AppEnvironment.fromKey(BuildConfig.APP_ENV)
AppEnvironmentConfigHolder.initialize(environment)
AppLogger.enabled = BuildConfig.DEBUG   // release 包一律关闭

AppEnvironmentConfigHolder.environment.collect { env -> ... }   // 订阅

// 测试包热切换（设置页）

```

下一次请求即生效，无需重启。

## 九、lib.router + lib.navigation —— 导航

导航刻意拆成**契约**与**实现**两层：

```
lib:router        纯 Kotlin：AppRoute 路由表 + Navigator 契约   ← 零平台依赖
lib:navigation    实现层：Navigation Compose                    ← 可整体替换
```

**为什么这么拆？** 业务页面只依赖 `lib:router`，所以将来 iOS 端换成
Decompose / 原生导航时，**业务代码一行不动**。

### 定义路由（lib:router）

```kotlin
@Serializable
data object HomeRoute : AppRoute

@Serializable
data class DetailRoute(val id: String) : AppRoute   // 参数在编译期校验
```

必须是 `@Serializable` —— Navigation 的类型安全路由靠它存取参数，
并且进程被杀后能从 back stack 恢复。

### 导航契约

```kotlin
interface Navigator {
    fun navigate(route: AppRoute)
    fun navigateUp(): Boolean
    fun popTo(route: AppRoute, inclusive: Boolean = false): Boolean
}
```

### 接线（app）

```kotlin
val navController = rememberNavController()

AppNavHost(navController = navController, startDestination = HomeRoute) {
    composable<HomeRoute> {
        HomeScreen(onOpenSettings = { navController.navigate(SettingsRoute) })
    }
    composable<DetailRoute> { entry ->
        val route = entry.toRoute<DetailRoute>()      // 类型安全取参
        DetailScreen(id = route.id, onBack = { navController.navigateUp() })
    }
}
```

`AppNavHost` 内部已 `ProvideNavigator`，页面里也可直接：

```kotlin
val navigator = LocalNavigator.current
navigator.navigate(DetailRoute("42"))
```

### 混合架构：Activity 壳 + Compose 内导航

本项目采用大厂常见的**混合式**结构：

```
┌─ MainActivity（主壳）─────────────────────┐
│  NavHost {                                 │
│    FeatureGraph × N  ← Hilt 自动聚合        │
│  }                                         │
└────────────────────────────────────────────┘
        │ 跨壳跳转 startActivity
        ▼
┌─ DetailActivity（独立壳）──────────────────┐
│  AbstractMviActivity + 单个 VM              │
└────────────────────────────────────────────┘
```

| 页面类型 | 用什么 | 例子 |
|---|---|---|
| 常规业务页（占绝大多数）| **壳内 Compose destination** | 首页、设置、列表、详情 |
| 特殊流程页 | **独立 Activity 壳** | 扫码、拍照、WebView、独立全屏 |

**判断标准**：
- 需要独立启动（外部 App / 通知 / 深链唤起）→ 独立壳
- 需要独立任务栈或特殊 launchMode → 独立壳
- 其余一律壳内 Compose

> 💡 **一屏一 Activity 的真实代价**：Manifest 线性膨胀（真实项目可达 400+ 条 / 2700+ 行）
> 且跳转无编译期校验。混合架构把大多数页面收进壳内，Manifest 只剩几个壳。
>
> 反过来，独立壳的好处是**没有中央注册表** —— 每个 Activity 自己声明。
> 所以「页面多」不该用 Activity 解决，而是「壳少、页面在壳内」。

### 路由注册：Hilt 自动聚合，宿主零引用

**`MainActivity` 不引用任何具体页面**：

```kotlin
@AndroidEntryPoint
class MainActivity : ComponentActivity() {

    @Inject
    lateinit var featureGraphs: Set<@JvmSuppressWildcards FeatureGraph>

    override fun onCreate(savedInstanceState: Bundle?) {
        // ...
        AppNavHost(navController, startDestination = HomeRoute) {
            featureGraphs.forEach { it.register(this) }   // 自动装配
        }
    }
}
```

每个 feature 贡献自己的路由图：

```kotlin
// app/feature/home/HomeNavigation.kt   ← 页面自己拥有
private val HomeGraph = FeatureGraph { builder ->
    builder.composable<HomeRoute> {
        val navigator = LocalNavigator.current
        val context = LocalContext.current
        val viewModel: HomeViewModel = hiltViewModel()

        HomeScreen(
            viewModel = viewModel,
            onOpenDetail = { id ->                              // 跨壳
                context.startActivity(DetailActivity.intent(context, id.toString()))
            },
            onOpenSettings = { navigator.navigate(SettingsRoute) },   // 壳内
        )
    }
}

@Module
@InstallIn(SingletonComponent::class)
object HomeGraphModule {
    @Provides @IntoSet
    fun provideGraph(): FeatureGraph = HomeGraph
}
```

**新增页面只动 feature 自己的文件，`MainActivity` 零改动。**

### 依赖注入（Hilt）

| 场景 | 写法 |
|---|---|
| ViewModel | `@HiltViewModel class XxxVM @Inject constructor(repo: Repo)` |
| 路由参数 | 构造参数用 `SavedStateHandle`（Activity extra 与路由参数都会进这里）|
| Application 级依赖 | `@Module @InstallIn(SingletonComponent::class)` |
| Composable 取依赖（无 VM）| `EntryPointAccessors`（见 `di/AppEntryPoints.kt`）|

> ⚙️ **构建注意**：Hilt 插件与 KSP **必须在同一作用域声明**（都在根 `build.gradle.kts`
> 或都在子模块），否则报 `The KSP plugin was detected to be applied but its task class
> could not be found`。

### 与 iOS 的兼容性（已就绪）

本项目**已经使用** JetBrains 的 KMP 移植版导航：

```toml
# gradle/libs.versions.toml
jetbrains-navigation-compose = {
    group = "org.jetbrains.androidx.navigation", name = "navigation-compose"
}
```

它**同一套 API 支持 android / iosArm64 / iosSimulatorArm64 / macos / jvm**，
且在 Android 上是 androidx 版的**直接替换**（同 API、同包名，已验证构建与测试无回归）。

所以 `FeatureGraph`、`AppNavHost`、`AppRoute`、`Navigator` 这层**不需要为 iOS 重写**。

| 层 | iOS 就绪度 |
|---|---|
| `AppRoute` / `Navigator`（纯 Kotlin）| ✅ 直接复用 |
| `FeatureGraph` / `AppNavHost`（导航装配）| ✅ 换 JetBrains 版后即可复用 |
| Hilt（DI）| ❌ 需换 Koin / kotlin-inject（Hilt 不支持 KMP iOS）|

## 十三、testFixtures —— ViewModel 单测

给 MVI ViewModel 写单测只需声明「意图流 + 期望状态序列 + 期望事件序列」，
订阅、派发、断言样板全部由基类完成。

### 用法

```kotlin
class XxxViewModelTest :
    BaseMviViewModelTest<XxxIntent, XxxState, XxxEvent, XxxViewModel>() {

    private val repository = mockk<XxxRepository>()

    @Test
    fun `load success produces loading then content`() {
        coEvery { repository.load() } returnsWithDelay ApiResult.Success(DATA)

        runVMTest(
            vmProducer = { XxxViewModel(repository) },
            intents = flowOf(XxxIntent.Load),
            expectedStates = listOf(
                expectExact(XxxState()),                                  // stateIn 初始值
                expectThat { assertTrue("Loading 应可见", it.isLoading) },  // 中间态
                expectExact(XxxState(items = DATA, loaded = true)),        // 终态
            ),
            expectedEvents = emptyList(),
        )
    }
}
```

### API

| 名字 | 作用 |
|---|---|
| `runVMTest(...)` | 订阅状态/事件 → 派发意图 → 断言序列 |
| `expectExact(value)` | 精确匹配（data class 相等）|
| `expectThat { }` | 自定义断言（列表、时间戳、浮点）|
| `preProcessingIntents` | 预热意图：先跑到某个起点，再开始断言 |
| `otherAssertions` | 额外校验（如验证 mock 调用次数）|
| `loggingEnabled` | 打开后打印状态/事件流转，定位断言失败 |
| `returnsWithDelay` | **mockk 延迟 1ms 返回**，规避 StateFlow 合流 |
| `delayEach()` | Flow 值之间插 1ms 延迟 |

### ⚠️ 两个必须知道的坑

**1. StateFlow 会合流掉瞬时中间态**

mock 瞬时返回时，`Loading → Success` 之间没有挂起点，收集器只能看到最后一个值
（kotlinx.coroutines#3120）。**用 `returnsWithDelay` 即可**：

```kotlin
coEvery { repository.load() } returnsWithDelay ApiResult.Success(DATA)
```

**2. `flatMapLatest` 会取消上一个请求**

连发意图（如 `flowOf(Load, Retry)`）时，后一个意图会取消前一个的请求 —— 这是
**预期行为**（天然防抖），只产生 3 个状态。若想验证「失败后再重试」，
用 `preProcessingIntents`：

```kotlin
runVMTest(
    vmProducer = { XxxViewModel(repository) },
    preProcessingIntents = flowOf(XxxIntent.Load),   // 先跑完（失败）
    intents = flowOf(XxxIntent.Retry),               // 再单独验证重试
    ...
)
```

## 十四、统一标题栏

`AbstractMviActivity` / `AbstractMviFragment` 已内置标题栏，样式对齐微信：
**左返回 / 中标题（绝对居中）/ 右操作区**。

标题**绝对居中**，左右区域悬浮其上、宽度互不影响；状态栏内边距由组件内部处理。

### 在 Activity/Fragment 基类里覆写

```kotlin
class DetailActivity :
    AbstractMviActivity<DetailIntent, DetailState, DetailEvent, DetailViewModel>() {

    override val vm: DetailViewModel by viewModels { ... }

    /** 中间标题：可由状态推导 */
    override fun titleBarConfig(state: DetailState) =
        TitleBarConfig(title = "详情 #${state.id}")

    /** 右侧操作区：文字 / 图片 / 自定义 */
    @Composable
    override fun TitleBarActions(state: DetailState) {
        TitleBarTextAction(if (state.favorite) "已收藏" else "收藏") {
            sendIntent(DetailIntent.ToggleFavorite)
        }
    }

    @Composable
    override fun render(state: DetailState) { ... }
}
```

### 三个可覆写点

| 成员 | 作用 | 默认 |
|---|---|---|
| `titleBarConfig(state)` | 标题文案与样式 | 取 manifest 的 `android:label` |
| `TitleBarActions(state)` | 右侧操作区 | 空 |
| `onTitleBarBackClick()` | 自定义返回逻辑，返回 true 表示已处理 | `false`（基类执行 `finish()` / `popBackStack()`）|

### 右侧操作区的三种写法

```kotlin
actions = {
    // 1) 文字
    TitleBarTextAction("保存") { save() }

    // 2) 图片（Painter：painterResource / rememberVectorPainter 等）
    TitleBarIconAction(
        painter = painterResource(R.drawable.ic_scan),
        contentDescription = "扫一扫",
    ) { scan() }

    // 3) 任意自定义内容（头像、带角标的图标…）
    TitleBarCustomAction(onClick = { openProfile() }) {
        AppImage(url, Modifier.size(28.dp).clip(CircleShape))
    }
}
```

### 常见配置

```kotlin
// 首页 / Tab 页：不要返回箭头
override fun titleBarConfig(state: HomeState) = TitleBarConfig(title = "首页", showBack = false)

// 全屏页（闪屏、播放器）：不要标题栏
override fun titleBarConfig(state: SplashState): TitleBarConfig? = null

// 自定义配色（如深色标题栏）
override fun titleBarConfig(state: S) = TitleBarConfig(
    title = "扫码",
    backgroundColor = Color(0xFF1A1A1A),
    contentColor = Color.White,
)
```

非 Activity 基类的页面（走 `MviScreen`）直接放组件即可：

## 十五、常见问题

**Q：新增 lib 模块要改哪里？**
`settings.gradle.kts` 里 `include(":lib:<name>")`。

**Q：为什么不用 Hilt？**
脚手架刻意保持依赖最少。当前用「Application 持有 + 构造注入」，页面依赖通过 ViewModel 工厂传入。项目变大后可平滑接入 Hilt，`lib` 层无需改动。

**Q：为什么路由不用 Navigation Compose？**
当前 router 是纯 Kotlin（可单测、依赖少），入口集中在 `MainActivity`。后续要接系统返回键或深链，可在这层适配而不影响业务页面。
